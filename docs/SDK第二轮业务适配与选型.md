# Agent SDK 第二轮测试与选型

日期：2026-10-16。范围：本地测试，不修改云服务，不切换正式运行引擎。模型适配不参与评分。

## 结论

建议本项目优先使用 **LangChain 的 create_agent 作为共享执行层**，不为 13 个工作区分别手写 LangGraph 流程图。Pydantic AI 是可行备选；本轮没有发现必须迁移到它才能解决的业务问题。Strands 也能完成任务，但目前没有显示出足够抵消工具参数适配成本的优势。

这不是三家能力的绝对排名：统一条件下，三家均通过真实业务链。推荐依据是业务能力已满足、工具与参数接入方式、异常策略可控，以及本项目已有接入和测试的维护成本。不能只凭本轮速度、GitHub 星数或一次演示选型。

## 实际测试了什么

版本：LangChain 1.4.6、Pydantic AI 2.56.0、Strands Agents 1.61.1。

统一业务工具：读取允许项目的 V2 输入 → 按参数计算 → 调用现有成本代码导出原始 Excel 模板。计算和导出使用 server/f7_project_demo.py 中的实际函数；测试资料为固定的两条物料，不写正式数据库，不发布成果、不发送通知。

真实调用统一使用简单工具参数，避免把模型对嵌套参数的不同处理混进 SDK 比较。每家测试默认 40 人天三次、Skill 改成 50 人天三次，共 **18 次，全部通过**。另有一批嵌套参数诊断调用，仅保留排错记录，不计入推荐。

固定故障测试由本地模拟模型网关发送相同的工具调用，用于检查 SDK 行为，不代表大模型的业务理解能力。11 类 × 3 家，共 33 个结果。

| 测试 | LangChain | Pydantic AI | Strands |
|---|---|---|---|
| 读取、计算、原模板导出 | 通过 | 通过 | 通过 |
| 负数工时拒绝进入计算，再接收正确参数 | 通过 | 通过 | 通过 |
| 普通读取异常，默认是否恢复继续 | 安全停止 | 安全停止 | 自动把异常反馈给模型后恢复 |
| 显式配置读取异常恢复策略 | 通过 | 通过 | 通过 |
| HTTP 503，不产生虚假成果 | 通过 | 通过 | 通过 |
| 请求其他项目被业务权限工具拒绝 | 通过 | 通过 | 通过 |
| 取消异步操作，取消后不写文件 | 通过 | 通过 | 通过 |
| 模型反复调用，限制执行次数 | 通过 | 通过 | 通过 |
| F5、F8 共用执行层的只读上下文 | 通过 | 通过 | 通过 |
| 结构化结果先错误后纠正 | 通过 | 通过 | 通过 |

表中 F5、F8 合计两类。默认异常停止不属于越权或虚假成功，但不满足“自动恢复后继续”的验收项。补充显式策略后，三家都能恢复。仅对可重试读取错误做恢复，不自动重试发布等写操作。

## Excel 与 Skill 验证

- 40 人天总额 106,115.87，修改 Skill 为 50 人天后总额 129,084.87。
- 三家最新的六份导出文件均复核金额缓存与原模板样式，全部正确。
- 完整导出检查包括七个工作表、工作表名称、ZIP 文件条目、styles.xml、合并单元格、列布局、打印设置和绘图引用保留。
- 文件能力来自共享业务导出代码，不能算某家 SDK 的独有优势。
- Skill 工时修改是自然语言覆盖默认值的实跑验证；不等于所有任意自然语言都已可靠编译成表单。

## 真正有用的差异

| 决策项 | 发现 | 对本项目的影响 |
|---|---|---|
| 工具参数 | LangChain、Pydantic AI 接受测试中的 Annotated + Field 约束；Strands 当前版本拒绝这种写法 | Strands 可改为 Pydantic 参数模型并显式 model_validate，能解决，但需要统一工具适配规范 |
| 异常策略 | Strands 默认把普通工具异常交回模型；另外两家需要显式中间件或 ModelRetry | 不能把所有错误一概重试。项目应自己规定哪些读取可重试，哪些写入必须停止 |
| 结构化输出 | 三家都能拒绝非法结果并纠正 | 无决定性胜负 |
| 权限与资料版本 | 三家均通过同一业务工具实现 | SDK 不负责替代账号权限、项目授权、文件版本表和发布规则 |
| 全局复用 | 三家均可共用执行器并注入不同岗位配置 | 13 个岗位不需要 13 个互相对话的 Agent；各自使用本岗位 Skill 和工具权限 |
| 当前代码维护 | 本项目已有 LangChain/LangGraph 的接入与测试基础 | LangChain 能沿用现有基础。Pydantic AI 迁移可行，但本轮未证明迁移收益高于成本 |

LangChain 的 create_agent 内部使用 LangGraph；使用它不意味着需要为每个岗位设计复杂状态图。应把岗位差异留在 Skill、工具集合和项目输入中。

## 资源与成本

| 项目 | LangChain | Pydantic AI | Strands |
|---|---:|---:|---:|
| 六次真实调用进程峰值内存最高值 | 127.4 MiB | 116.6 MiB | 118.7 MiB |
| 当前安装环境的依赖文件估算 | 39.5 MiB | 33.5 MiB | 62.0 MiB |

内存是单次测试 Python 进程，包含成本表依赖；不是完整服务，也不是 2GB Linux 并发容量测试。依赖大小含客户端及传递依赖，来自当前安装文件统计，不是新增部署体积。三家环境并非完全相同，因此这些数字只用于排除明显资源风险，不用于细微排名。现阶段没有证据说明 SDK 本身会成为 2 核 2GB 的主要瓶颈，仍需对整套服务做目标机器压测。

三家均可自行托管使用开源代码；模型、存储、服务器及可选托管观测服务另计。市场接受度与用户评价不由本轮测试证明，不能把下载数当真实企业用户数。可维护性方面应同时看官方文档、发布记录、真实案例和本团队调试体验，而不是宣称某家“口碑最好”。

官方资料：[LangChain 工具](https://docs.langchain.com/oss/python/langchain/tools)、[Pydantic AI 工具](https://pydantic.dev/docs/ai/tools-toolsets/tools/)、[Strands 发布记录](https://github.com/strands-agents/sdk-python/releases)。本轮没有做用户评价的系统抽样，市场评价不列为已验证结论。

## 建议采用的边界

1. 一个共享 Agent 执行器，接收用户、项目、工作区、Skill 版本、已引用资料版本和允许工具。
2. 账号权限、项目访问、资料版本、计算、Excel/Word 导出继续由业务服务负责。工具执行时再次校验权限，不只依赖提示词。
3. 人工确认后才发布成果；发布由业务代码创建下游协作通知。模型没有自行发布和修改负责人权限。
4. 先替换执行层的接口，不重做 13 个工作区，不改变用户已熟悉的交互。

## 尚未验证，不应夸大

- 全部 13 个工作区的端到端业务、真实多用户并发及 Linux 整机容量。
- 进程被杀后的任务恢复、同步 Excel 写入中途强制取消。
- 所有复杂 Skill 修改对参数界面的稳定编译。
- 大资料集检索、跨项目资料隔离的全面安全审计。
- 三家社区评价的系统调查；实际用户数量和市场占有率没有可靠统一口径。

这些不妨碍当前技术推荐，但正式切换前应至少验收：两个销售隔离项目、引用指定版本、修改 Skill 后试运行、原模板导出、人工发布与下游通知。执行层替换还没有在本轮自动进行。
