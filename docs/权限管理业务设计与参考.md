# 权限管理：项目协作业务设计

2026-10-16

## 业务判断

管理的核心不是给人打几个勾，而是确定一个人在某个项目中的职责。账号、岗位、项目参与和岗位负责人分别建模；同一项目同一岗位只能有一个负责人，一个人可以参与或负责多个项目。F7/F8 的销售参与者可以保存个人 Skill 草稿并试运行，只有销售负责人可以应用本项目流程；公共发布由管理员执行。

原界面的问题：先列全公司用户，再在同一项目里重复列负责人和所有用户，管理员无法直接判断“这个人实际能做什么”；逐个勾选项目不能解释负责人自动获得的访问权限。

## 成熟产品参考与采用点

- [GitLab 项目成员](https://docs.gitlab.com/user/project/members/)：按项目列实际成员，区分成员关系带来的授权来源，提供搜索、角色过滤和成员管理。采用“实际成员表 + 明确访问来源”，避免把所有账号当成项目成员。
- [Jira 添加项目成员](https://support.atlassian.com/jira-software-cloud/docs/add-people-to-team-managed-projects/)：项目角色与站点账号分离。采用“项目分配职责，人员页管理岗位”的分工。

参考的是交互和授权表达，不引入其产品角色名或另一套组织层级。GitLab 可有多个高权限成员，本系统仍严格执行每项目每岗位唯一负责人。

## 页面

默认打开项目授权：选择项目 → 查看实际成员。一个成员一行，显示岗位、项目身份、资料访问、F7/F8 Skill 调试、项目流程应用和正式处理工作区。

添加成员只选择已有用户，先获得参与权限；设置或交接负责人单独处理。交接显示原负责人、新负责人和具体影响，并选择是否保留原负责人项目访问。界面不做即时后台改动，确认后一次提交。

人员与岗位页反查一个用户的项目权限，项目表展示其负责人或参与者身份以及调试/应用能力；可以跳到该项目管理。不再展示所有项目的可勾选清单。

岗位权限保留规则查询，变更记录展示负责人从谁交给谁以及访问保留选择。人员页和项目页都仅管理员可见。

## 后端与验证

实际权限由后端根据账号状态、管理员身份、岗位、项目成员和负责人关系计算后返回，前端不自行猜测。停用用户不显示可执行权限。

负责人替换、原负责人访问保留/撤销在同一数据库事务执行；继续检查 expected_revision，旧页面提交失败时不改变任何授权。不改现有真实账号、项目授权，不新增数据库表。

测试覆盖：参与者可调试但不能应用；未授权项目不可读；停用用户不能操作；负责人直接成员关系移除后仍通过职责获得访问；交接撤销/保留访问；旧版本交接拒绝且不产生部分修改。
